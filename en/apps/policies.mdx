There is no separately published, complete developer policy for gugu Apps yet, and no separate CONTRIBUTING file, review time limit or appeal process. Current requirements come from product API limits, the index repository's README and check scripts, and maintainer code review on each PR. Below, enforced rules are kept apart from recommendations.

## Rules enforced today

- The market only accepts packages built from a pinned source commit. The source must be public and reviewable; an archive of unknown origin is not accepted.
- Published versions cannot be changed or deleted, and their version numbers are never reused. Withdrawal, end of maintenance and unlisting go through registry fields.
- Pages are bound by the sandbox and network rules. Request extra capabilities in the manifest; the person agrees on gugu's confirmation sheet and can later revoke them one by one.
- Apps that provide local programs, skills or standing instructions must request `agents:tools`. Programs run with the person's local rights, and the install sheet shows the actual command.
- `firstRun` is only allowed on Apps whose code is in the first-party index repository. Other Apps are never installed silently.
- Maintainers review and merge every registration on its PR. Passing CI does not publish an App by itself.

## What to explain when you submit

So people can judge your App and maintainers can review it, state in the README and the PR description:

- The main purpose, and the reason for each permission and network host.
- Which outside services it contacts, what data it keeps, where, and what uninstalling clears.
- Supported devices and client versions.
- Where the person sets up any account connection. Never put keys inside the package.

When you use third-party libraries or copy sample code, check and keep their licenses. The manifest's `license` is plain text; the platform does not verify it.

Starting and contacting Agents spends the person's quota. Explain when the App starts or contacts Agents, and never let Agents wake each other endlessly. Read shared data only within what the caller may access.

## Data and interaction boundaries

Everyone in a shared file may read its content. Identity cards, keys or anything meant for one person cannot be protected just by hiding them in the page; design the data boundary following the in-product `apps-together` guide.

Show text written by others with `textContent` or a rendering method that escapes it. When a file call fails, show the reason; a failed read must never look like no data. Revoked permissions and offline states also need an explanation the person can act on.

These implementation recommendations come from the in-product App guides. There is currently no separate content policy, commercial terms or review commitment.
