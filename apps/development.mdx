先让 App 在自己的测试材料上完成一次真实工作，再准备上架。这一页讲开发循环、页面能做什么、人会看到哪些错误，以及怎样写测试。

## 开发循环

<Steps>
  <Step title="从文件夹安装">
    左栏「App」→「装本地文件夹」→ 选择包含 `manifest.json` 的文件夹。不申请权限的 App 直接装上；有权限时咕咕先显示确认单，由你同意。
  </Step>
  <Step title="改代码">
    在原文件夹里改。咕咕安装时会复制一份，所以改动要重新安装后才生效。不要直接修改或软链咕咕数据目录里的文件。
  </Step>
  <Step title="重新安装">
    再点「装本地文件夹」，选同一个文件夹。同一个 id 会被替换。没有新增权限时直接装上；新增了权限会再次显示确认单。
  </Step>
  <Step title="重新打开并检查">
    重新安装会让页面从入口重新加载。按下文的清单检查一次真实操作。
  </Step>
</Steps>

从文件夹装的 App 在产品页显示为「从文件夹装的」（manifest 写了 `author` 时显示作者）。有人从聊天卡片安装同一个 App 时，会看到「这台装的是从文件夹装的开发版 1.0.0」这类提示，卡片不会替换你的开发版。从文件夹装的 App 只在这台电脑上。

也可以请咕咕里的 Agent 制作和检查。它用产品内的 `app_create`、`app_install`、`app_check` 工具；`app_check` 会以隐藏页面运行 App，读回加载结果、错误、页面快照和截图。装到这台电脑上的权限仍由你确认。

## 页面的沙箱

页面运行在独立的来源上。下面的限制由咕咕强制执行，不能通过声明绕开。

| 内容 | 规则 |
| --- | --- |
| 脚本 | 只能来自包内文件，用 `<script src>` 引入；内联脚本、CDN 脚本、`eval`、`new Function` 都不会运行 |
| 样式 | 包内 CSS 和内联样式都可以；推荐使用平台样式和 `--em-*` 主题变量 |
| 图片、字体、音视频 | 来自包内、`data:`/`blob:`，或 `network` 声明过的 HTTPS 主机 |
| 网络请求 | 只能用 HTTPS 和 WSS 访问声明过的主机；`http:` 即使主机已声明也会被拒；本机、内网名和 IP 地址一律拒绝 |
| 嵌套与表单 | 不能嵌入 iframe、object；不能提交表单 |
| 系统访问 | 没有 Node、`require`、Electron 接口、文件系统访问接口；不能打开新窗口；不能读取咕咕或其他 App 的页面 |
| 弹窗 | 不能用 `alert`、`confirm`、`prompt`；用 `gugu.modal` |

工具程序不受页面沙箱约束，它以使用者的本机权限运行。安装确认单会原样显示程序的启动命令。

页面隐藏或移动后通常仍在运行，切换页签不会让它重新加载。重启咕咕、升级 App 或撤销权限会从入口重新加载。重要数据写进共享文件或 App 私有数据，不要只放在内存里。

## 人会看到的错误

| 情况 | 人看到什么 | 怎么处理 |
| --- | --- | --- |
| 清单不合法 | 「安装失败」，附上出错的字段和原因 | 按提示改清单；字段规则见 [manifest 参考](/apps/manifest) |
| `apiVersion` 太高 | 提示需要更新咕咕，并写出这台客户端支持的最高版本 | 更新客户端，或降到所用接口需要的版本 |
| `apiVersion` 低于 3 | 提示这是旧接口，请改写为当前版本 | 按当前接口改写 |
| 缺 `platforms` 或声明错误 | 「安装失败」，说明 `platforms` 的问题 | 写 `["desktop"]`、`["phone"]` 或两者，`apiVersion` 至少 12 |
| 拒绝或关闭权限确认单 | App 没有装上 | 说明为什么需要这项权限，再试一次 |
| 页面调用失败 | 由 App 自己显示；调用 `reportError` 时也记入 App 错误记录 | 每个调用都处理失败，写清原因 |
| 工具程序出错 | Agent 在工具结果里看到错误；人在 App 页面上看到 | 程序已安装不代表已成功运行，检查启动命令和依赖 |

## 检查一次真实操作

1. 安装后打开页面，确认它能点、能输入，错误有明确的显示位置。
2. 保存一条数据，关掉再打开，确认它还在。共享 App 再请另一位成员打开同一个文件检查。
3. 切换明暗主题，把页面拉窄，检查键盘操作、中文输入和按钮名称。
4. 撤销一项已授权的权限，确认功能说明了失败原因；重新授权后再试。
5. 制造「没有数据」和「读取失败」两种情况，确认显示不同。
6. 准备一份应当失败的清单，例如把 id 写成 `notes.starter`，确认它被拒绝。

## 自动测试

### 索引仓的 CI 测什么

每个提到索引仓的 PR 都会运行：

1. `npm test`：即 `node --test scripts/*.test.mjs`，检查索引仓自己的脚本。
2. `node scripts/app-tests.mjs`：对 `sources/` 下每个 `package.json` 里写了 `scripts.test` 的 App，在它的目录里运行 `npm ci` 和 `npm test`。`devDependencies` 里有 `playwright` 的，会先安装 Chromium。一个 App 失败，其余 App 照样跑完。
3. `node scripts/verify.mjs --base origin/<目标分支>`：重新打包并检查新增版本，详见[提交到 App 市场](/apps/publishing)。

代码在你自己仓库里的 App 不会被索引仓 CI 运行测试。测试放在你的仓库里，由你在自己的仓库里运行，例如用 GitHub Actions。

### 推荐写法

把逻辑写成不依赖 `window.gugu` 的模块，再用 Node 自带的测试运行器测试。官方的[协作看板](https://github.com/GUYI-AI/gugu-apps/tree/main/sources/kanban)就是这样组织的：

```text
kanban/
  package.json        "test": "node --test test/*.test.mjs"
  test/core.test.mjs
  app/                ← 实际打进包的目录
    manifest.json
    lib/core.js
```

```js
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { emptyBoard } from '../app/lib/core.js';

test('a new board has the four starting columns in order', () => {
  const board = emptyBoard();
  // 断言列的数量和顺序
});
```

测试、构建脚本和它们的 `package.json` 放在 App 目录之外，不会进入用户安装的包。只登记 `app/` 这个目录即可。打包会跳过 `node_modules` 和 `.git`，所以运行时依赖要以构建后的文件放进 App 目录。
